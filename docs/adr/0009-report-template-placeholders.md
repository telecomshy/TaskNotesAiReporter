# 报告模板占位符维持扁平替换并按引用注入

> **状态**：本文末尾的后果由 [ADR-0015](./0015-status-classification-owned-by-adapters.md) 收编：状态判定归各 来源 adapter，Tasks 侧用其 `status.type`（在其 adapter 内部），状态归类 为四档。但其中记录的限制**仍成立**——TaskNotes 侧「进行中」仍按状态值名判定、自定义状态名后会失效（其状态目录无类型字段）。其余决定不变。

「报告模板」此前只支持 `{{tasks}}` 与 `{{range}}`（另有一个恒为「报告」、未文档化的 `{{type}}`）。决定：新增占位符时**不引入模板引擎**——保持扁平的字符串替换，不支持循环、条件或字段访问；占位符**按引用注入**：模板引用哪个占位符，模型就只收到那份数据，因此可用状态子集占位符确定性地裁剪输入、控制 token。新增项只限「模型算不准或拿不到」的信息（生成日、精确计数、总耗时）与按状态切分的任务子集；不做项目 / 标签 / 上下文的去重汇总。同时把 `{{range}}` 的口径明确为**任务数据跨度**：所选任务在 完成 / 到期 / 计划 / 创建 四个日期字段上的最早~最晚（规范化为 `YYYY-MM-DD`），而非报告周期，也非「选择任务」里选定的筛选区间；由于创建日期恒存在，该范围恒有定义。

## Considered Options

- **引入模板引擎（循环 / 条件 / 字段访问）**：表达力强，但需自建解析器（转义、嵌套、循环），而下游是 LLM，分组与归纳它本就能做，边际收益低。
- **去重汇总占位符（`{{projects}}` / `{{tags}}` / `{{contexts}}`）**：模型能从完整任务列表读出，属纯重述，无增量。
- **让 `{{range}}` 由报告类型或筛选区间决定**：前者需要补上尚不存在的报告类型 UI，后者需要主窗口记录瞬态的筛选区间；两者都是独立功能，另立需求。

## Consequences

- `{{type}}` 保留在代码中以兼容，但不写入占位符文档；报告类型 UI 的缺失是独立问题。
- `CONTEXT.md` 的「日期范围」定义据此改写，并新增「筛选区间」以区分两个被混用的概念。
- 「进行中」在 TaskNotes 侧只能按状态值名（默认 `in-progress`）判定，用户自定义状态名后会失效；未来接入 Tasks 来源时改用其 `status.type`。
